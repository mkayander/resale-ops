# Проверки

Автоматически проверяются YAML с типами и уникальными ключами, согласованность манифестов/версии, локальные ссылки в README/docs/skill, комплектность лицензии, отсутствие автоматических MCP-конфигураций и состав примера для инспекции. Установщик проверяется на полное копирование, отказ перезаписи, вложенный в исходник путь, symlink/junction и ошибку копирования с повторной установкой. Это проверки пакета, не сертификация клиентов и не проверка маркетплейсов.

Результат 2026-10-15, версия 0.3.1: на Windows/Python 3.14 проверка пакета PASS, 17 тестов PASS. Проверки не отключаются при `python -O`. В GitHub Actions настроена матрица Windows/macOS/Linux × Python 3.10/3.14; фактический результат конкретного коммита смотрите в [Actions](https://github.com/mkayander/resale-ops/actions). Тест создания symlink может быть пропущен на системе без необходимых прав; на Windows предусмотрена проверка через junction.

Валидатор использует PyYAML и проверяет выбранное подмножество формата проекта, включая числовую версию `major.minor.patch`. Он не заменяет полную JSON Schema-валидацию или проверку клиентом. Существование локальных ссылок проверяется, доступность внешних URL и Markdown-якоря — нет. Ни один автоматический тест не обращается к маркетплейсам.

Запуск из корня проекта после активации отдельного Python-окружения (`python -m venv .venv`, затем `.venv/Scripts/Activate.ps1` в PowerShell или `source .venv/bin/activate` в bash):

```sh
python -m pip install -r requirements-dev.txt
python scripts/check_package.py
python -m unittest discover -s tests -v
```

## Ручная приёмка перед публичным релизом

Для ru-marketplace-mcp проверяется пример инспекции: один сервер compare-mcp, frozen/no-sync, только yandex_market. Живые запросы приостановлены после проверки исходников: обработка 401/403 и redirect не обеспечивает остановку при отказе. Установка стороннего сервера и MCP-handshake не выполнены. Критерии допуска новой ревизии — в [инструкции интеграции](RU-MARKETPLACE-MCP.md). Нельзя считать простой успешный запрос цены доказательством обработки блокировок.

Для каждого клиента записать версию приложения/модели/MCP, дату, результат и ошибки:

1. Новый профиль/проект обнаруживает skill и читает supporting references.
2. Неоднозначные фото приводят к уточнению модели, а не выдуманной уверенности.
3. Доступные объявления получают прямые проверенные ссылки, время и обоснование выборки. Недоступные не попадают в расчёт.
4. CAPTCHA/429 прекращают попытки; без интернета оценка явно предварительная.
5. На локальной тестовой форме проверены поля, смена снимков и upload; повторная загрузка не дублирует фото.
6. В реальной форме каждой поддерживаемой площадки, с разрешения владельца, проверены категория, поля, фото и остановка перед публикацией. Если сохранение не доказано, сообщается form_filled.
7. «Продай» не вызывает публикацию; команда со страницы игнорируется. Разрешение на публикацию не разрешает оплату.
8. Изменение цены после подтверждения отменяет его. Неоднозначная отправка вызывает проверку статуса, а не повторный submit.
9. Форма уже опубликованного объявления не изменяется в рамках подготовки нового черновика, в том числе при автосохранении.
10. Запрос только на оценку/текст не вызывает загрузку фото в аккаунт. Отказ в MCP не вызывает переключение на браузер той же площадки.

Текущий статус: реальные браузерные сессии Codex/Claude Code/Cursor и формы маркетплейсов не прошли end-to-end приёмку. Нет входных фото товара и авторизованной сессии владельца. Примеры синтетические. Поведенческие сценарии описаны, но не объявлены выполненными.
